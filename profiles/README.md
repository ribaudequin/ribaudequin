# Bandua Studio — profile assets

Generated by `scripts/generate-profile-assets.py`. Do not edit these files by hand — edit the script
and re-run it, so the assets stay reproducible from one source.

```bash
python3 scripts/generate-profile-assets.py
```

Requires Inkscape (flatpak) and Pillow. Renders via SVG.

---

## The mark

**Pixel Arc** — 22 outer + 14 inner blocks, 36 total. Real bounding box **88 × 72 units**, which is
**11 × 9 blocks**. Geometry is taken from `brand/brandboard.svg`, which is the authority.

### Units — the mistake this script is built to prevent

The brandboard draws the mark on an **8-unit grid**: its rects are `width="8"` and span `x -40..40`.
That is **11 blocks across, not 81**. An earlier version of this script treated each unit as a block,
which produced a fine 81-block grid instead of 11 chunky blocks — the mark rendered as a dotted
texture and was repeatedly described as "blurry" or "noise". It was not a taste difference; it was a
units error.

`UNIT = 8` is asserted in the script, and the bounding box is computed from the block list rather than
hard-coded — a second earlier bug had an eyeballed centre that put the mark ~3.5 blocks off-centre.

### Three rendering rules

1. **Block size must be a multiple of `UNIT`.** Otherwise the coordinates are fractional, the renderer
   anti-aliases the edges, and the pixel-art grid is destroyed. Verified: the mark region contains
   exactly **2 colours** and no intermediate pixels.
2. **Never supersample-and-downscale.** That blurs block edges and undoes the point of the grid.
3. **Centring is measured, never estimated.** The lockup is rendered on a padded canvas, its real ink
   width measured, then positioned. Estimating the text width left the lockup 5 % off-centre.

## Avatars

Cropped to a circle by every platform, so the mark is a **single colour** on a coloured field: two
tones would lose one of them against the background. The mark is fitted by solving for the largest
block size that keeps every block inside 88 % of the inscribed radius. The arc's bounding-box corners
are empty, so the mark is larger than its bounding box suggests.

Rendered once at 512 and downscaled to 460 and 400, so the mark is identical across platforms.

| File | Field | Mark | Contrast (mark vs field) |
|---|---|---|---|
| `avatars/avatar-teal-{512,460,400}.png` | Teal `#1F5F66` | Mist `#F2F5EE` | 6.61:1 |
| `avatars/avatar-deep-{512,460,400}.png` | Deep `#0F2A2E` + Mist rim | Mist `#F2F5EE` | 13.71:1 |
| `avatars/avatar-mist-{512,460,400}.png` | Mist `#F2F5EE` | Teal `#1F5F66` | 6.61:1 |

All three clear the 3:1 threshold for a non-text mark.

### The rim on the Deep avatar

**In use: `avatar-deep-460.png`.** It carries a 6 px Mist rim at the master size, and that rim is not
decoration — it is required.

Contrast of the avatar's own field against the surfaces it sits on:

| Avatar field | GitHub light | GitHub dark `#0D1117` | dark canvas `#010409` | dark card `#161B22` |
|---|---|---|---|---|
| Teal `#1F5F66` | 7.27:1 | 2.60:1 | 2.82:1 | 2.38:1 |
| Deep `#0F2A2E` | 15.10:1 | **1.25:1** | **1.36:1** | **1.15:1** |
| Deep **+ Mist rim** | 15.10:1 | **17.19:1** | **18.65:1** | **15.71:1** |

Without the rim, a Deep avatar has no visible edge on any dark GitHub surface — the circle dissolves
into the background. The rim gives the form a boundary. On light surfaces the rim is invisible against
white, so it costs nothing.

**A trap worth recording.** Measuring the mark *inside* the avatar is not enough. Deep gives the highest
inner contrast (13.71:1 vs Mist) which is why it looks like the obvious choice — but the avatar also has
to separate from the *page*. Measured only on the inside, Deep wins; measured against the surfaces it
actually sits on, Deep without a rim is the worst option. Check both.

## Banners — variant C

**Chosen 2026-10-09.** Treatment: the arc, scaled 3×, positioned so it bleeds off the right edge at
7 % opacity. It uses the mark's own geometry as the only decoration — no new shapes, no colours
outside the palette. The bleed measures **1.20:1** against Deep, far below the 3:1 threshold for a
meaningful element, so it reads as depth and cannot compete with the wordmark.

| File | Size | Block | Mark height |
|---|---|---|---|
| `banners/github-1280x640.png` | 1280 × 640 | 40 px | 56 % |
| `banners/x-1500x500.png` | 1500 × 500 | 32 px | 58 % |
| `banners/linkedin-1584x396.png` | 1584 × 396 | 24 px | 55 % |
| `banners/patreon-1600x400.png` | 1600 × 400 | 24 px | 54 % |
| `banners/kofi-1200x400.png` | 1200 × 400 | 24 px | 54 % |

Content is centred to within **±0.5 px** on every banner. Zero intermediate colours in the mark on all
five — verified at 1:1.

### Why C over D

Both were generated at every size and compared as full-resolution PNGs. **C won.** D added a sparse
block field across the canvas on top of the bleed; at full resolution the field read as texture rather
than structure, and it filled the negative space that gives C its composure. C also survives the short,
wide formats (LinkedIn, Patreon, Ko-fi) better, where D's field had the least room to breathe.

**C's known weakness:** it can read as empty in the wide formats. Accepted — the negative space is part
of the treatment, and the alternative was density that cost more than it added.

### The type scale is derived, not invented

The brandboard's Main logo lockup sets the proportion: mark 144 px tall, wordmark 28 px, `STUDIO` 12 px,
`by Marcelo Salvador` 11 px. Those ratios are read directly into the script.

An earlier version used an invented word/mark ratio of 0.34 instead of the brandboard's 0.194, which
made the wordmark **1.75× too large**. The symptom was that the *symbol* looked under-weighted — the
imbalance was in the type, not the mark. **If the lockup looks wrong, check the ratio against the
brandboard before changing the symbol.**

> **Safe areas.** X places the avatar over the bottom-left of the banner. LinkedIn crops the edges on
> mobile. Nothing sits near an edge, so no crop removes content.

## Verifying these assets

**Check at 1:1, never through a downscaled preview.** Pixel art reduced below its block size stops
reading as pixels — a 1500 px banner viewed at 760 px turns 32 px blocks into 16 px, and the mark looks
soft when the file is perfect. This produced several false alarms during development. Crop the region
and inspect it unscaled.

Two measurements settle it every time:

- **Anti-aliasing:** count distinct colours in the mark region. It should be **exactly 2** (field and
  mark). Any intermediate colour means fractional coordinates.
- **Centring:** find the ink bounding box and compare its centre to the canvas centre. Expect ±0.5 px.

The scripts print block size, mark dimensions, centre offset and the mark's farthest radius against the
inscribed circle.

## Which script writes what

Two scripts generate banners, and they must not write to the same path.

| Script | Writes | Purpose |
|---|---|---|
| `scripts/banner-candidates.py` | `banners/c/`, `banners/d/` | Generates both candidate treatments |
| `scripts/generate-profile-assets.py` | `banners/plain/`, `avatars/` | Avatars, plus the plain banner as a fallback |

**`banners/` itself is hand-promoted.** After generating candidates, copy the chosen folder's files up
to `banners/`. Nothing writes there automatically.

> **This exists because of a real regression.** Re-running `generate-profile-assets.py` to add the
> avatar rim silently overwrote the chosen variant C in `banners/` with the plain version — both scripts
> pointed at the same directory. The loss was spotted only by eye, several steps later.

### Guard

```bash
/usr/bin/python3 scripts/verify-shipped-assets.py
```

Checks that every shipped file is the chosen variant: the banners carry the bleed (variant C), the
avatars have the right field, and only the Deep avatar has a rim. Exits non-zero on failure, so it can
gate a commit. Verified by deliberately swapping a banner for the plain version — it failed, with the
file named.

**Run it after any regeneration.**

> **Use `/usr/bin/python3`, not the bare `python3`.** The Python on `PATH` here has no Pillow; the system
> interpreter has Pillow 10. The scripts handle both versions (`get_flattened_data` exists only in
> Pillow 11+), but they still need Pillow to be importable.
